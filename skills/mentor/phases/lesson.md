# Phase: Lesson

Goal: teach the current milestone's concepts properly, grounded in the learner's repo, BEFORE they build. Chat is the teacher; the HTML page is the visual aid they revisit. Style contract: `references/lesson-style.md`.

## Steps (in order)

1. **Re-read the relevant repo files.** Real paths and resource names. A lesson that could have been written without the repo is a failed lesson.
2. **Prerequisite check, then ledger.** List the milestone's concepts and, for each, what it presupposes (`Prerequisites:` in PLAN.md; add them if the plan lacks them). For every prerequisite with no evidence (no ledger card above `encountered`, nothing demonstrated in the session or the repo): teach it before the milestone lesson. One or two missing → fold them into layer (a) of this lesson. Several missing → write a fundamentals lesson first (its own NNNN, e.g. `0002-go-fundamentals.html`), ordered so each section builds on the previous, then continue with the milestone lesson. Then check the ledger for the milestone concepts themselves and pick the method per concept using `references/methods.md` (worked example first for true novices, struggle-first only with adjacent prior knowledge); record the picks and reasons in the journal.
3. **Orient in chat first.** Before any page: the problem each concept exists to solve, framed as an engineering situation ("Postgres acknowledged the commit and lost power 5 ms later..."), the simplest mental model, why an engineer cares, and where useful one breath on the surrounding solution space (the neighbouring options and why this one). Short. This is teaching, not a quiz: questions here are predictions from intuition only, never from mechanism not yet taught.
4. **Write the visual aid** to `STATE_DIR/lessons/NNNN-<slug>.html` (NNNN increments). Three layers in order:
   - **(a) Concept.** Anchor analogy, term, one worked example (toy domain or the repo's shape), the seam where it leaks. Diagrams and flows where they beat prose. One primary source. For code: the runtime picture first (what the machine does at each line: memory, copies, control flow), syntax second; worked examples carry 3 to 5 subgoal labels naming the purpose of each step ("open resource", "guard error", "release"); interference points from the baseline get an explicit "in <old language> this means X, here it means Y" line.
   - **(b) This repo.** Map the concept onto real files: "in your repo, X at `path` is the thing that...".
   - **(c) Do it yourself.** Task spec for the deliverable: what to build, constraints, definition of done, "commit a prediction in chat before running X" pointers (question named, answer absent). No solution code for the deliverable. Doc links. **No quiz, multiple-choice, or reveal blocks anywhere in the page** (`references/lesson-style.md`).
4b. **Write the mentor's reference** for features (`Stage: middle | later`) to `STATE_DIR/lessons/NNNN-<slug>.reference.md` per `references/reference-format.md`: behaviour, invariants, design families, trade-offs, failure modes, misconceptions, evaluation criteria; no intended layout or sequence. For early units, at most five lines (definition of done, two or three misconceptions) or nothing. Private: never shown or quoted. Update when the build reveals a missing trap or design family.
4c. **Check the unit's load.** Count the unknowns this lesson's exercise combines (`references/progression.md`). Early unit over one or two → split the exercise, or move one dimension into a focused lab, before opening the page.
5. **Open it** (`open <file>` on macOS, `xdg-open` on Linux), then **return to chat**: 2 to 3 stage-appropriate prompts (predict, explain the model back, apply to the repo). Open questions first; multiple choice only as second choice (vague open answer, or distractor discussion after a correct one): 3 to 4 options, learner picks and justifies, then discuss the distractors (each encodes a misconception). Wrong answers get diagnosed and repaired, not "try again". Before the build starts, one short say-back of the milestone's load-bearing model (the one the deliverable depends on), in the learner's words; not a recitation of every concept on the page.
6. **Ledger and journal.** Concepts taught here become `introduced` only after that say-back (teaching explanation labeled as Claude's in "My model"); the rest stay `encountered` honestly. Note lesson number, method picks, and the unknowns count in the journal. Mark milestone `lesson-done` in PLAN.md.

Early units (`Stage: early`) keep the page short and the exercise tiny: one model, one piece of syntax or tooling, one guided application walked in chat, one independent application the learner does alone. A test belongs in the exercise from the first unit when there is a pure function to test.

Session may end here; build can start immediately if the learner wants. Reading the page is not evidence; the build is where practice happens.
