# Phase: Lesson

Goal: teach the current milestone's concepts properly, grounded in the learner's repo, BEFORE they build. Chat is the teacher, one concept per message (SKILL.md "Explaining"). The HTML page is optional: write it only when a diagram or a worked example beats chat (`references/lesson-style.md`).

## Steps (in order)

1. **Re-read the relevant repo files.** Real paths and resource names. A lesson that could have been written without the repo is a failed lesson.
2. **Measure, then design** (`references/lesson-design.md`): list the strands the milestone rests on (`Prerequisites:` in PLAN.md; add them if the plan lacks them), probe every strand without ledger evidence, write the design (objective, floor, chain, cuts, expected misses) before any lesson text. **No lesson text from a guessed floor.** Pick the method per concept (`references/methods.md`); record picks and reasons in the journal.
3. **Orient in chat first.** Before any page: the problem each concept exists to solve, framed as an engineering situation ("Postgres acknowledged the commit and lost power 5 ms later..."), the simplest mental model, why an engineer cares, and where useful one breath on the surrounding solution space (the neighbouring options and why this one). Depth follows the design: full for chain concepts, one sentence for neighbours. This is teaching, not a quiz: questions here are predictions from intuition only, never from mechanism not yet taught.
4. **Optionally write the visual aid** (skip it when chat suffices) to `STATE_DIR/lessons/NNNN-<slug>.html` (NNNN increments). Three layers in order:
   - **(a) Concept.** Each chain concept at textbook depth per SKILL.md "Explaining", in the order of the chain. For code: the runtime picture first (what the machine does at each line: memory, copies, control flow), syntax second; worked examples carry 3 to 5 subgoal labels naming the purpose of each step; interference points from the baseline get an explicit "in <old language> this means X, here it means Y" line (`references/methods.md`, programming formats). Drawn from the canonical teaching text where one exists (Kerrisk for Linux syscalls, Stevens for TCP, Kleppmann for data systems), named by title and chapter; the content is embedded, the citation is for going further. Official docs linked for the mechanism.
   - **(b) This repo.** Map the concept onto real files: "in your repo, X at `path` is the thing that...".
   - **(c) Do it yourself.** Task spec for the deliverable: what to build, constraints, definition of done, "commit a prediction in chat before running X" pointers (question named, answer absent). No solution code for the deliverable. Doc links.
4b. **Write the mentor's reference** for features (`Stage: middle | later`) per `references/reference-format.md`. For early units, at most five lines (definition of done, two or three misconceptions) or nothing. Private: never shown or quoted. Update when the build reveals a missing trap or design family.
4c. **Check the unit's load.** Count the unknowns this lesson's exercise combines (`references/progression.md`). Early unit over one or two → split the exercise, or move one dimension into a focused lab, before opening the page.
5. **If a page was written, open it** (`open <file>` on macOS, `xdg-open` on Linux). In chat, run the sequence: worked example (mentor), completion problem (learner fills one or two steps), then the build is the independent problem. Prompts here are say-backs and worked-example steps only; the material is minutes old, so no cold predictions from mechanism. Open questions first; multiple choice only as second choice (`references/methods.md`, menu). Wrong answers get diagnosed and repaired, not "try again". Before the build starts, one short say-back of the milestone's load-bearing model (the one the deliverable depends on), in the learner's words; not a recitation of every concept on the page.
6. **Ledger and journal.** Concepts taught here become `introduced` only after that say-back (teaching explanation labeled as Claude's in "My model"); the rest stay `encountered` honestly. Note lesson number, method picks, and the unknowns count in the journal. Mark milestone `lesson-done` in PLAN.md.

**Lab projects.** When the repo has a `labs/SPEC.md`, the lesson artifact is a lab directory, not an HTML page and not chat: `LESSON.md` (the chain from the design, one concept per screen, checks named and unanswered) plus the lab card, skeleton, stages and hints per that spec. Steps 3 to 5 then happen inside the files and the streamed session; the say-back of the load-bearing model happens at the top of the build.

**Lesson size.** A lesson is one chain of concepts at full depth; no length rule on a concept or a page. A chain that runs long is split into two lessons (two NNNN), never compressed; the curriculum can be long, a lesson cannot.

Early units (`Stage: early`) keep the chain to one or two concepts and the exercise tiny: one model, one piece of syntax or tooling, one guided application walked in chat, one independent application the learner does alone. A test belongs in the exercise from the first unit when there is a pure function to test.

Session may end here; build can start immediately if the learner wants. Reading the page is not evidence; the build is where practice happens.
