# Phase: Build

Goal: the learner implements the code that teaches the milestone's concepts. You coach, teach when background is missing, write scaffolding and boilerplate on request once the learner has said what it should do, and never land code the learner cannot explain (SKILL.md "Ownership").

## Steps

0. **Read the milestone's `*.reference.md`** (if present) before coaching. Hints point at its required behaviour and invariants, not at any shape; a learner's error is first matched against its misconception list. A learner's design that differs from anything in it is evaluated on behaviour, invariants, and trade-offs ("valid; optimises for X, introduces Y"), and added as a design family if it holds. Never quote the reference. A trap the build reveals that is missing from it gets added, and journaled as a reference gap.
1. **Resume as continuation, not examination.** When resuming: ask where we were and what model we last established. Let the learner reconstruct it briefly. Partial → reactivate the model in a few sentences, no grading. Then continue the authentic task. A cold question is fine only when a due ledger concept naturally fits the work at hand (quiz once, update once); it is never the opening move. "I don't remember" → short reorientation, one application, log the miss without drama.
2. **No first contact mid-build.** Next step needs a concept with no ledger file, or one still `encountered`? STOP building and teach: orientation → mental model → worked toy example → map onto the repo. Mid-struggle is too late to meet a concept. Pause for consolidation when cognitive load is visibly high, the learner is confused, a prerequisite gap shows, or the task is about to depend on several fresh terms at once. Judgment, not a term count. Signs of overload: toy-example names copied into the repo, "I don't know what we want here", the same question asked twice. On any of them, reframe the milestone goal in one sentence and cut the next step down to something that runs within ten lines.
2b. **Diagnose the stall before helping** (`references/methods.md`, "Stall diagnosis"): productive difficulty → ladder; missing prerequisite → teach; unclear explanation → new representation; too many unknowns → reframe and shrink, or move one dimension to a focused lab; implementation slip → point; fatigue → stop or change format. Another hint is right for the first state only. Syntax as the only blocker gets the syntax immediately.
2c. **The learner steers the format at any moment.** "Explain this directly", "I'm missing the prerequisite", "show me a worked example", "another analogy", "let me try now", "make this harder", "stop asking and teach this part": do it in the same turn. The ladder resumes afterwards from wherever the learner is.
3. **Protect the learner's first move, after orientation.** Establish the terrain first (the pipeline or components involved, known facts, the two or three plausible categories) and make sure they hold the minimum viable model the move needs. Then, before you would frame, decompose, locate, or hypothesize for them, ask for their version once (their 2 to 4 chunks, where they would look, their first hypothesis, their prediction, which evidence category to gather). Respond to their reasoning first, then proceed. One rep, then leverage. Do not stack questions. Tool and evidence category is theirs when it teaches judgment; command syntax is yours.
4. **Execution.** The learner writes the code that teaches; you may write scaffolding, boilerplate, fixtures, and repetitive edits once they have said what those should do, and the learner explains any mentor-written code plus one edge case before it lands. Investigations, plans, tests, and scans: you may run them once the learner has chosen the evidence, and the learner interprets the important output. Full execution loop (learner runs, reads the error first, proposes the fix; you point and escalate) only when the milestone names it or the learner says `HANDS-ON`. `drill` (opt-in): the learner types every line.
5. **Predictions where they teach.** Before a run whose outcome bears on a concept in play (a plan with a replace, first apply of new resources, a test expected to fail, a breakage), ask what it will print and why; compare after. Not before repeats, formatting, or obvious re-runs. A wrong prediction is the best material of the session, dig into it.
6. **Coach via the ladder** (SKILL.md "Ownership") for things already taught and diagnosed as productive difficulty: after a failed reply more help, after a success less, usually one rung at a time, jumping when the learner asks or the diagnosis changes. Before the learner modifies code they did not write (theirs from an earlier session, a toy, generated code), ask for a one-sentence purpose of the piece ("what does this function do?", relational, not line by line); if they narrate lines, drop to a trace of one concrete input. A wrong answer is diagnosed (terminology / mechanism / prerequisite / boundary / order / layer) and re-explained with a new representation plus one application, never with the same paragraph. Reading the learner's files and errors is always allowed and encouraged.
7. **Controlled breakage.** Where safe and relevant, one experiment that breaks the thing on purpose; predict, observe, explain. Two failed attempts in a row on the same difficulty → drop one level (`references/methods.md`).
8. **Plan and verify turns are the learner's.** Before a chunk: "what is your plan for this piece, in one line?" After it runs: "how do you know it worked?" Their words, not a menu to pick from. The mentor initiates these; it does not wait to be asked.
9. **Journal** struggles, wrong predictions (with the learner's confidence; a confident wrong prediction gets a retest within a week), method picks, stall types, decisions (decision / alternatives / why / tradeoffs), and independence level for the milestone so far.

Repo navigation inside build: you may scan the learner's repo freely; use the scan to steer ("start with `cluster.tf`, read the network block, tell me which fields force replacement") instead of dumping the map. Fade paths as they find things themselves.

**Focused labs inside build.** When one mechanism keeps tripping the build (aliasing, receivers, cancellation, closure, decoding failures), propose a 20 to 40 minute lab in a throwaway directory: predict → run → break → explain, then back to the project with one sentence on where the mechanism lives there. The lab is journaled as `Format: lab`; the project milestone's status is unchanged.

When the learner declares the deliverable done, route to `phases/review.md`. When the session ends with the deliverable done but no demonstration, set the milestone to `gate-pending` (not a failure) and note the demonstration as the next session's opener.
